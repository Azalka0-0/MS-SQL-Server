## 1. Транзакция

**Транзакция** --- последовательность операций, производимых над базой данных и переводящих базу данных из одного согласованного состояния в другое согласованное состояние.

Транзакция также рассматривается как **неделимое действие над базой данных** и логическая единица работы системы.

Основная задача СУБД --- обеспечивать согласованность данных при конкурентном выполнении транзакций и восстанавливать согласованность после отказов.

---

## 2. Свойства ACID

ACID --- четыре основных требования к транзакциям:

- **Atomicity --- Атомарность**;
- **Consistency --- Согласованность**;
- **Isolation --- Изолированность**;
- **Durability --- Долговечность**.

### Atomicity --- Атомарность

Каждая транзакция представляет собой единицу работы.

Она не может быть разбита на меньшие части.

Выполняются либо все действия, определённые в транзакции, либо не выполняется ни одно из них.

### Consistency --- Согласованность

После выполнения транзакции данные переходят из одного согласованного состояния в другое.

Для поддержания согласованности используются:

- правила;
- проверки;
- ограничения;
- триггеры.

### Isolation --- Изолированность

Конкурирующие транзакции физически обрабатываются изолированно друг от друга.

Для пользователей это выглядит так, как будто транзакции выполняются параллельно.

### Durability --- Долговечность

Если транзакция завершена успешно, изменения, произведённые ею в данных, не должны быть потеряны даже при последующих ошибках.

---

## 3. Согласованность в базах данных

База данных находится в **согласованном состоянии**, если для этого состояния выполнены все ограничения целостности.

**Ограничение целостности** --- утверждение, которое может быть истинным или ложным в зависимости от состояния базы данных.

Конкурентное использование ресурсов корректными программами может привести к некорректным результатам.

Нарушения согласованности могут быть вызваны:

- отказами программ-клиентов;
- отказами СУБД;
- отказами операционной системы;
- отказами оборудования.

Функция СУБД --- гарантировать согласованность при конкурентном выполнении и восстановление согласованности после отказов.

---

## 4. Транзакции, истории и расписания

База данных состоит из элементов данных:

``` text
x, y, z, ...
```

Операции:

``` text
r(x) --- чтение
w(x) --- запись
```

**Транзакция** --- конечная последовательность операций.

**История** --- упорядоченная совокупность операций нескольких транзакций.

**Расписание** --- префикс истории.

Пример истории:

``` text
r1(x) r2(x) w1(x) w2(x) c1 c2
```

---

## 5. Проблемы конкурентного выполнения

При конкурентном выполнении транзакций могут возникать:

- потеря обновлений;
- несогласованное чтение;
- грязное чтение;
- неповторяющееся чтение;
- фантомное чтение.

### Потеря обновлений

Две транзакции считывают один и тот же элемент и затем записывают изменённые значения.

Пример:

``` text
r1(x) r2(x) w1(x) w2(x)
```

Обновление первой транзакции может быть перезаписано второй.

### Несогласованное чтение

Одна транзакция читает связанные данные, в то время как другая транзакция изменяет их между операциями чтения.

### Грязное чтение

Транзакция считывает данные, записанные другой транзакцией, которая впоследствии выполняет откат.

### Неповторяющееся чтение

Одна транзакция повторно считывает данные, а другая транзакция изменяет их между операциями чтения.

В результате повторное чтение возвращает другое значение.

### Фантомное чтение

При повторном выполнении запроса могут появиться новые строки, соответствующие условию поиска, либо исчезнуть ранее найденные строки.

---

## 6. Серийное расписание

**Серийное расписание** --- расписание, в котором все операции любой транзакции либо предшествуют, либо следуют за операциями любой другой транзакции.

Серийное расписание всегда корректно.

---

## 7. Конфликты

**Конфликт** --- пара операций расписания, которая одновременно удовлетворяет условиям:

- операции принадлежат разным транзакциям;
- операции работают с одним элементом данных;
- по крайней мере одна операция является операцией записи.

Конфликты присутствуют в любом нетривиальном расписании.

### Эквивалентность расписаний

Расписания считаются эквивалентными, если их множества конфликтов совпадают.

Расписание называется **серийным по конфликтам**, если оно эквивалентно по конфликтам серийному расписанию.

---

## 8. Граф конфликтов

**Граф конфликтов (граф серийности)** используется для определения сериализуемости расписания.

- вершины соответствуют транзакциям;
- дуги проводятся для каждого конфликта в направлении конфликта.

Расписание серийно по конфликтам тогда и только тогда, когда граф серийности **не содержит контуров**.

Если граф не имеет контуров, эквивалентное серийное расписание можно построить с помощью топологической сортировки.

---

## 9. Сериализуемость по коммутативности

Основные свойства:

- любые операции чтения коммутируют;
- любые операции над разными элементами коммутируют.

Расписание сериализуемо по коммутативности, если его можно преобразовать в серийное расписание перестановками соседних операций.

Сериализуемость по коммутативности эквивалентна сериализуемости по конфликтам.

---

## 10. Использование блокировок

Для обеспечения корректности конкурентного выполнения используются блокировки.

Основные операции:

``` text
lr(x) --- блокировка на чтение, совмещаемая
lw(x) --- блокировка на запись, монопольная
ur(x) --- снятие блокировки на чтение
uw(x) --- снятие блокировки на запись
```

Замки для одного элемента данных несовместимы, если они устанавливаются разными транзакциями и хотя бы один из них является замком на запись.

Попытка установить несовместимый замок переводит транзакцию в состояние ожидания.

Основные проблемы блокировок:

- корректность;
- тупики;
- производительность.

---

## 11. Протокол двухфазной блокировки 2PL

**2PL (Two-Phase Locking)** --- двухфазный протокол блокирования.

Для каждой операции необходимо предварительно установить замок.

Транзакция не может устанавливать новые замки после того, как она сняла какой-либо замок.

Две фазы:

1. установка блокировок;
2. снятие блокировок.

Двухфазный протокол генерирует расписания, сериализуемые по конфликтам.

---

## 12. Тупики и бесконечные ожидания

При использовании блокировок возможны:

- бесконечные ожидания;
- тупики (deadlock).

Возможные способы решения:

- устанавливать очередь ожидания, возможно с приоритетами;
- устанавливать порядок получения блокировок;
- разделять установку и снятие блокировок;
- периодически проверять наличие тупиков и выполнять рестарт транзакции.

### Граф ожиданий

Вершины графа --- активные транзакции.

Дуга проводится из ожидающей транзакции в транзакцию, установившую несовместимую блокировку.

**Тупик имеет место тогда и только тогда, когда в графе ожиданий имеется контур.**

Транзакции, попавшие в тупик, должны быть оборваны.

---

## 13. Протокол для деревьев WTL

**WTL** применяется, когда база данных структурирована как дерево.

Основные правила:

- все замки --- на запись;
- для установки замка необходимо иметь замок на родительской вершине, кроме корня;
- один элемент не блокируется дважды одной транзакцией;
- снятие замков возможно в любое время и не препятствует установке новых замков.

### Корректность WTL

Граф сериализуемости ацикличен.

Транзакции сериализуются в том порядке, в котором они устанавливают замки на корень.

Протокол WTL свободен от тупиков.

---

## 14. Диспетчер транзакций

Модель СУБД включает:

- диспетчер транзакций;
- исполнитель запросов.

Основные требования к диспетчеру транзакций:

- корректность;
- производительность.

Используются:

- пессимистические протоколы;
- оптимистические протоколы.

## 15. Виды транзакций в SQL Server

В SQL Server используются:

- **автоматическая фиксация транзакций**;
- **неявные транзакции**;
- **явные транзакции**.

### Автоматическая фиксация

Это режим по умолчанию.

Каждая отдельная инструкция Transact-SQL фиксируется после завершения.

Специальные инструкции для управления транзакциями не требуются.

### Неявные транзакции

Неявный режим включается:

``` sql
SET IMPLICIT_TRANSACTIONS ON
```

Новая транзакция неявно начинается после завершения предыдущей.

Каждая транзакция явно завершается:

``` sql
COMMIT
ROLLBACK
```

### Явные транзакции

Явная транзакция начинается инструкцией:

``` sql
BEGIN TRANSACTION
```

и завершается:

``` sql
COMMIT
ROLLBACK
```

---

## 16. Фазы транзакции

Основные фазы:

``` text
Установить уровень изоляции
        ↓
BEGIN TRANSACTION
        ↓
SQL-операции
        ↓
COMMIT или ROLLBACK
```

Уровень изоляции задаётся инструкцией:

``` sql
SET TRANSACTION ISOLATION LEVEL
```

---

## 17. Размер транзакций

Логически транзакция должна объединять только выполнение взаимосвязанных операций.

Если транзакция слишком большая и содержит последовательность несвязанных операторов, то любой сбой, автоматически выполняющий откат транзакции, может отменить действия, которые могли бы быть успешно завершены при использовании более коротких транзакций.

---

## 18. Уровни изоляции

Уровень изоляции задаётся инструкцией:

``` sql
SET TRANSACTION ISOLATION LEVEL
    { READ UNCOMMITTED
    | READ COMMITTED
    | REPEATABLE READ
    | SNAPSHOT
    | SERIALIZABLE
    }
```

Основные уровни:

``` text
READ UNCOMMITTED
READ COMMITTED
REPEATABLE READ
SNAPSHOT
SERIALIZABLE
```

---

## 19. READ UNCOMMITTED

Блокировки на чтение не устанавливаются.

Транзакции могут считывать строки, изменённые другими транзакциями, но ещё не зафиксированные.

Это позволяет выполнять **грязное чтение**.

Значения данных могут изменяться до окончания транзакции, а строки могут появляться и исчезать в наборе данных.

Это уровень с наименьшим ограничением из представленных уровней изоляции.

---

## 20. READ COMMITTED

Нельзя считывать данные, изменённые другими транзакциями, но ещё не зафиксированные.

Таким образом, грязное чтение не допускается.

Однако считанные данные могут быть изменены другими транзакциями во время работы текущей транзакции.

Возможны:

- неповторяющееся чтение;
- недействительные результаты чтения;
- фантомное чтение.

`READ COMMITTED` установлен в SQL Server по умолчанию.

---

## 21. REPEATABLE READ

Нельзя считывать данные, которые были изменены, но ещё не зафиксированы другими транзакциями.

Совмещаемые блокировки применяются ко всем считываемым данным и сохраняются до завершения транзакции.

Это запрещает другим транзакциям изменять строки, считанные текущей транзакцией.

Другие транзакции могут вставлять новые строки, соответствующие условиям поиска текущей транзакции.

При повторном чтении диапазона могут появиться новые строки-фантомы.

---

## 22. SNAPSHOT

`SNAPSHOT` копирует состояние данных на момент начала транзакции.

Текущая транзакция не видит изменения данных, произведённые другими транзакциями после её запуска.

Считывание данных транзакцией моментального снимка не блокирует запись данных другими транзакциями.

Если транзакция пытается записать данные, изменённые другой транзакцией после её начала, она прерывается.

Перед использованием необходимо включить параметр базы данных:

``` sql
ALTER DATABASE Database
SET ALLOW_SNAPSHOT_ISOLATION ON;
```

Проверить состояние можно:

``` sql
SELECT name,
       snapshot_isolation_state,
       snapshot_isolation_state_desc
FROM sys.databases;
```

После включения изоляции моментального снимка обновлённые версии строк для каждой транзакции содержатся в `tempdb`.

Отказ от блокировок чтения способствует снижению вероятности взаимоблокировок в сложных транзакциях.

---

## 23. SERIALIZABLE

Нельзя считывать данные, изменённые другими транзакциями, но ещё не зафиксированные.

Другие транзакции не могут изменять данные, считываемые текущей транзакцией.

Другие транзакции не могут вставлять новые строки со значениями ключа, попадающими в считываемый диапазон, до завершения текущей транзакции.

При повторном чтении будет получен тот же набор строк.

Блокировки считанного диапазона сохраняются до завершения транзакции.

Из-за низкого параллелизма этот уровень рекомендуется использовать только при необходимости.

---

## 24. Сводная таблица уровней изоляции

| Уровень | Основные особенности | Возможные проблемы |
|---|---|---|
| `READ UNCOMMITTED` | Нет блокировок на чтение | грязное чтение, неповторяющееся чтение, фантомное чтение |
| `READ COMMITTED` | Не читаются незафиксированные изменения | неповторяющееся чтение, фантомное чтение |
| `REPEATABLE READ` | Блокировки считанных данных сохраняются до завершения | фантомное чтение |
| `SNAPSHOT` | Используются версии данных на момент начала транзакции | конфликт при записи изменённых данных |
| `SERIALIZABLE` | Блокируется считываемый диапазон | низкий параллелизм |

## 25. Именование транзакций

Можно использовать переменную:

``` sql
@tran_name_variable
```

содержащую допустимое имя транзакции.

Пример:

``` sql
BEGIN TRANSACTION Tr1;
```

## 26. BEGIN TRANSACTION

`BEGIN TRANSACTION` начинает транзакцию.

Синтаксис:

``` sql
BEGIN { TRAN | TRANSACTION }
    [ { transaction_name | @tran_name_variable } ]
```

---

## 27. COMMIT

`COMMIT` фиксирует транзакцию.

После фиксации изменения, внесённые транзакцией, становятся постоянными.

При использовании блокировок освобождаются объекты, заблокированные транзакцией.

Пример:

``` sql
BEGIN TRANSACTION;

-- SQL-операции

COMMIT;
```

---

## 28. Вложенные транзакции

При использовании вложенных транзакций фиксация внутренней транзакции не освобождает ресурсы и не делает её изменения постоянными.

Изменения становятся постоянными и ресурсы освобождаются только при фиксации внешней транзакции.

Каждый `COMMIT TRANSACTION` уменьшает значение:

``` sql
@@TRANCOUNT
```

Когда `@@TRANCOUNT` становится равным нулю, внешняя транзакция фиксируется.

Функция:

``` sql
@@NESTLEVEL
```

возвращает уровень вложенности транзакций.

Аргумент `transaction_name` не учитывается компонентом Database Engine при определении вложенности.

При откате вложенной транзакции откатываются все внешние транзакции.

---

## 29. SAVE TRANSACTION

`SAVE TRANSACTION` устанавливает точку сохранения внутри транзакции.

Синтаксис:

``` sql
SAVE { TRAN | TRANSACTION }
    { savepoint_name | @savepoint_variable }
```

Точка сохранения позволяет выполнить откат к определённому месту, не отменяя всю транзакцию.

Пример:

``` sql
BEGIN TRANSACTION;

INSERT INTO ValueTable VALUES(1);

SAVE TRAN SavePoint1;

INSERT INTO ValueTable VALUES(2);

ROLLBACK TRAN SavePoint1;

INSERT INTO ValueTable VALUES(3);

COMMIT TRANSACTION;
```

В одной транзакции может быть несколько точек сохранения.

---

## 30. ROLLBACK

`ROLLBACK` откатывает транзакцию к её началу или к заданной точке сохранения.

Синтаксис:

``` sql
ROLLBACK { TRAN | TRANSACTION }
    [ transaction_name
    | @tran_name_variable
    | savepoint_name
    | @savepoint_variable ]
```

Без `savepoint_name` или `transaction_name` выполняется откат к началу транзакции.

При наличии вложенных транзакций такой откат отменяет внутренние транзакции до начала самой внешней транзакции.

`ROLLBACK TRANSACTION` уменьшает `@@TRANCOUNT` до `0`.

Откат к точке сохранения не уменьшает `@@TRANCOUNT`.

---

## 31. Обработка ошибок

Для управления поведением транзакции при ошибках используется:

``` sql
SET XACT_ABORT { ON | OFF }
```

При:

``` sql
SET XACT_ABORT ON
```

ошибка Transact-SQL приводит к завершению и откату всей транзакции.

При:

``` sql
SET XACT_ABORT OFF
```

в некоторых случаях откатывается только инструкция, вызвавшая ошибку, а обработка транзакции продолжается.

В зависимости от серьёзности ошибки возможен откат всей транзакции.

`OFF` устанавливается по умолчанию.

---

## 32. XACT_STATE

`XACT_STATE` --- скалярная функция, которая сообщает о состоянии пользовательской транзакции текущего запроса.

Функция показывает, существует ли активная пользовательская транзакция и может ли она быть зафиксирована.

Пример:

``` sql
SELECT XACT_STATE();
```

Тип возвращаемых данных:

``` text
smallint
```

``` sql
    { sql_statement | statement_block }
END TRY
BEGIN CATCH
    [ { sql_statement | statement_block } ]
END CATCH;
```

Пример обработки ошибки:

``` sql
BEGIN TRY
    BEGIN TRAN

    -- SQL-операции

    COMMIT TRAN;
END TRY
BEGIN CATCH
    ROLLBACK TRAN;
END CATCH;
```

---

## 34. Lock timeout

Для ограничения времени ожидания блокировки используется:

``` sql
SET LOCK_TIMEOUT 2000;
```

Значение задаётся в миллисекундах.

Для бесконечного ожидания используется:

``` sql
SET LOCK_TIMEOUT -1;
```

---

## 35. Гранулярность блокировок

**Гранулярность** определяет уровень объекта, на котором устанавливается блокировка.

Основные уровни:

- `Table (TAB)` --- блокировка таблицы;
- `Extent (EXT)` --- блокировка экстента;
- `Page (PAG)` --- блокировка страницы;
- `Key (KEY)` --- блокировка ключа индекса;
- `RID` --- блокировка строки таблицы-кучи.

### Table

Самая грубая логическая блокировка, которую может использовать SQL Server.

### Extent

Используется при создании новых таблиц, расширении существующих объектов и увеличении файлов.

### Page

Может использоваться, когда SQL Server требуется одновременно заблокировать множество строк.

### Key

Используется для блокировки ключей в индексах.

`RID` применяется для строк таблиц-куч.

---

## 36. Высокая конкурентность и блокировки

Высокая конкурентность означает, что множество пользователей может работать одновременно.

По возможности этого достигают небольшими блокировками, чтобы не блокировать данные, необходимые другим пользователям.

С другой стороны, большие блокировки могут быть быстрее, чем установка большого количества маленьких блокировок.

---

## 37. Эскалация блокировок

**Эскалация блокировок (lock escalation)** --- процесс, при котором множество блокировок с маленькой гранулярностью преобразуется в одну блокировку на более высоком уровне иерархии с большей гранулярностью.

Причины использования больших блокировок:

- уменьшение количества блокировок;
- снижение накладных расходов;
- уменьшение потребления ресурсов.

### Проблемы маленьких блокировок

**Locking overhead** --- иногда одна крупная блокировка выгоднее большого количества мелких.

**Data contention** --- одна блокировка устанавливается атомарно, а установка нескольких блокировок уже не является одним атомарным действием.

**Resource contention** --- блокировки занимают место и требуют системных ресурсов, в том числе для проверки тупиков.

---

## 38. Подсказки оптимизатору

По умолчанию сервер старается использовать минимальную необходимую гранулярность.

Если блокировка отдельных записей не является оптимальной, сервер может выбрать больший объём блокировки.

Явно указать гранулярность можно с помощью подсказок:

``` text
ROWLOCK  --- блокировка на уровне записи
PAGLOCK  --- блокировка на уровне страницы
TABLOCK  --- блокировка на уровне таблицы
```

---

## 39. Восстановление

Основные задачи восстановления:

- индивидуальный откат транзакции;
- восстановление после внезапной потери содержимого оперативной памяти;
- восстановление после поломки основного внешнего носителя базы данных.

---

## 40. Отказы приложений

К отказам приложения относятся:

- выполнение `ROLLBACK` оператором;
- аварийное завершение прикладной программы;
- принудительный откат транзакции при взаимной блокировке.

---

## 41. Технические проблемы

### Мягкий сбой

Может произойти:

- при аварийном отключении электрического питания;
- при неустранимом сбое процессора.

Теряется та часть базы данных, которая на момент сбоя находилась в буферах оперативной памяти.

### Жёсткий сбой

Связан с поломкой основного внешнего носителя базы данных.

Основой восстановления являются:

- архивная копия;
- журнал изменений базы данных.

---

## 42. Возобновление после отказов

При отказах приложения или транзакции транзакции обрываются.

При отказе системы функционирование возобновляется после рестарта и восстановления согласованности базы данных.

При разрушении носителя выполняются:

1. рестарт;
2. восстановление из резервной копии;
3. восстановление согласованности базы данных.

---

## 43. Восстановление оборванных транзакций

Обрывы транзакций могут быть вызваны:

- ошибками при выполнении приложений;
- невозможностью выполнить транзакцию сериализуемым образом.

Операции записи можно отменять выполнением отката в обратном порядке.

---

## 44. Восстановимость расписаний

**Восстановимость расписания** означает, что транзакции должны фиксироваться до того, как их результаты используются другими транзакциями.

Пример невосстановимого расписания:

``` text
w1(x) w2(x) c2 a1
```

**S2L** --- двухфазный протокол с удержанием замков на запись до конца транзакции.

S2L гарантирует восстановимость.

---

## 45. Откат и фиксация

По команде:

``` sql
ROLLBACK
```

система откатывает транзакцию к началу, то есть к неявной точке отката.

По команде:

``` sql
COMMIT
```

система фиксирует изменения до неявной точки фиксации.

Если во время выполнения одной из команд возникает ошибка, система может откатить только ошибочную команду, отменив её результаты и сохранив прежнюю точку фиксации.

---

## 46. Оптимистический и пессимистический подходы

Для обеспечения целостности транзакции СУБД может откладывать запись изменений в базу данных до успешного выполнения всех операций и получения команды `COMMIT`.

Другой подход предполагает запись изменений в базу данных до завершения транзакции с сохранением старых значений данных на время её выполнения.

---

## 47. Сегмент отката

**Сегмент отката (rollback segment, RBS)** --- специальная область памяти на диске, в которую записывается информация обо всех текущих изменениях.

Обычно сохраняются старое и новое содержимое изменённых записей.

Это позволяет восстановить прежнее состояние базы данных при:

- `ROLLBACK`;
- ошибке текущей операции.

Данные в RBS хранятся до завершения транзакции, изменяющей эти данные.

---

## 48. Savepoint

**Savepoint** сохраняет промежуточное состояние для возможности вернуться к нему.

Можно выполнить:

``` text
ROLLBACK TO <имя_точки>
```

для отката от текущего момента до точки сохранения.

В одной транзакции может быть несколько точек сохранения.

---

## 49. Журнал транзакций

**Журнал транзакций** --- часть базы данных, в которую поступают данные обо всех изменениях объектов базы данных.

Обычно в журнале фиксируются:

- номер транзакции;
- состояние транзакции;
- точки сохранения;
- команды, составляющие транзакцию;
- другие сведения, необходимые для восстановления.

Журнал недоступен пользователям СУБД и поддерживается особо тщательно.

---

## 50. Ведение журнала

Журнал ведётся последовательно.

Используется принцип:

**WAL (Write-Ahead Log) --- опережающая запись в журнал.**

В журнале регистрируются:

- операции записи;
- начало транзакций;
- конец транзакций.

Каждая запись содержит данные:

``` text
undo --- для отката
redo --- для наката
```

При фиксации запись журнала обязательно записывается на диск.

---

## 51. Фиксация транзакции

При фиксации:

- изменения транзакции помечаются как постоянные;
- уничтожаются точки сохранения транзакции;
- освобождаются объекты, заблокированные транзакцией;
- транзакция помечается как завершённая в журнале;
- удаляются системные записи о транзакции из оперативной памяти.

---

## 52. Восстановление после системных отказов

Для восстановления после системного отказа необходим рестарт сервера базы данных.

Для возможности восстановления необходимо вести журнал обновлений.

При нормальной работе все изменения записываются в журнал.

После рестарта журнал используется:

- для повторения операций;
- для отката незавершённых транзакций.

---

## 53. Общие принципы восстановления

После восстановления должны выполняться два условия:

1. результаты зафиксированных транзакций должны быть сохранены;
2. результаты незафиксированных транзакций должны отсутствовать.

---

## 54. Алгоритм восстановления

При восстановлении необходимо:

1. определить зафиксированные транзакции;
2. определить активные и незавершённые транзакции;
3. при необходимости повторить изменения зафиксированных транзакций;
4. выполнить откат незавершённых до отказа транзакций.

---

## 55. Алгоритм восстановления при рестарте

Используются три фазы.

### Фаза просмотра

Определяются все зафиксированные и активные транзакции при прямом просмотре журнала.

### Фаза наката (redo)

При прямом просмотре журнала повторяются операции зафиксированных транзакций.

### Фаза отката (undo)

Журнал просматривается в обратном порядке.

Откатываются операции незавершённых транзакций.

---

## 56. Завершение восстановления

После завершения фазы отката необходимо:

1. записать на диск все изменённые блоки базы данных;
2. после записи базы данных очистить журнал;
3. возобновить нормальную работу системы.

---

## 57. Возможности журнала транзакций

Журнал поддерживает:

- восстановление отдельных транзакций;
- восстановление всех незавершённых транзакций при запуске SQL Server;
- откат восстановленной базы данных, файла, файловой группы или страницы до момента сбоя;
- поддержку репликации транзакций;
- поддержку решений высокой доступности и аварийного восстановления.

---

## 58. Усечение журнала транзакций

**Усечение журнала** освобождает место в файле журнала для повторного использования.

Оно необходимо для предотвращения переполнения журнала.

При усечении удаляются неактивные виртуальные файлы журнала из логического журнала транзакций.

Если усечение не выполняется, журнал со временем может занять всё доступное место на диске.

Усечение журнала выполняется автоматически.

---

## 59. Сжатие журнала

Усечение журнала не уменьшает размер физического файла журнала.

Для уменьшения физического размера файла используется сжатие.

Пример:

``` sql
DBCC SHRINKFILE (DataFile1, 7);
```

где:

- `DataFile1` --- имя файла;
- `7` --- размер в МБ.

---

## 60. Модель транзакций

Основные правила модели транзакций:

- `COMMIT` означает успешное завершение транзакции и делает изменения постоянными;
- `ROLLBACK` прерывает транзакцию и отменяет изменения, выполненные в её рамках;
- новая транзакция начинается непосредственно после `ROLLBACK`;
- успешное завершение программы, в которой была инициирована текущая транзакция, означает успешное завершение транзакции;
- ошибочное завершение программы прерывает транзакцию.

---

# Шпаргалка

``` text
BEGIN TRANSACTION       → начать явную транзакцию
COMMIT                  → зафиксировать изменения
ROLLBACK                → отменить изменения
SAVE TRANSACTION        → создать точку сохранения

@@TRANCOUNT             → число активных вложенных транзакций
@@NESTLEVEL             → уровень вложенности
XACT_STATE()            → состояние пользовательской транзакции

SET IMPLICIT_TRANSACTIONS ON
                        → включить неявные транзакции

SET XACT_ABORT ON       → при ошибке откатить всю транзакцию

SET LOCK_TIMEOUT 2000   → ожидание блокировки 2000 мс
SET LOCK_TIMEOUT -1     → бесконечное ожидание

READ UNCOMMITTED        → допускает грязное чтение
READ COMMITTED          → уровень по умолчанию в SQL Server
REPEATABLE READ         → удерживает блокировки считанных данных
SNAPSHOT                → чтение версий данных
SERIALIZABLE            → блокировка считываемого диапазона

lr(x) / ur(x)           → блокировка / снятие блокировки чтения
lw(x) / uw(x)           → блокировка / снятие блокировки записи

ROWLOCK                 → блокировка записи
PAGLOCK                 → блокировка страницы
TABLOCK                 → блокировка таблицы

undo                    → откат операций
redo                    → повторное выполнение операций
WAL                     → опережающая запись в журнал
```

## Главное

Транзакция объединяет связанные операции с базой данных в логическую единицу работы.

Для обеспечения корректности конкурентного доступа используются:

1. блокировки;
2. протоколы сериализации;
3. уровни изоляции;
4. точки сохранения;
5. журнал транзакций;
6. механизмы восстановления.

Основная задача этих механизмов --- сохранить согласованность базы данных при конкурентном выполнении транзакций и после отказов системы.
